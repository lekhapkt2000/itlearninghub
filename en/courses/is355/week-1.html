01 · PART A - THEORY

Context: Finance oriented toward sustainable development (ESG)

Modern financial activity does not focus on profit alone - it also assesses a business's impact on the environment, society, and governance.

  • E (Environmental): The environment, Carbon emissions, energy, climate change (the focus of IS355).
  • S (Social): Workers, communities, customer rights.
  • G (Governance): Governance, transparency, business ethics, risk control.

02 · GREEN FINANCE & THE DATA PROBLEM

Green Finance & the Data Problem (ESG Data)

Green Finance is the use of financial resources to support activities that have a positive impact, or reduce a negative impact, on the environment (renewable energy, green transport, reducing Carbon emissions).
ESG Score / Green Project ↓ Risk Assessment ↓ Credit Decision ↓ Interest Rate / Limit Incentives

The data challenge (Data Integrity & Transparency)

When a company claims "We have cut Carbon emissions by 30%," banks and investors need to verify: Where does the data come from? Has it been altered? Who audited it? Blockchain acts as an immutable ledger to solve this data integrity problem.

03 · CARBON CREDIT

Carbon Credit

A Carbon Credit is a unit representing the right to emit, or the amount of greenhouse gas (1 tonne of CO2), that has been reduced/removed.
Green Project ↓ Emission Measurement ↓ Verification (Audit) ↓ Carbon Credit Issuance ↓ Trade / Offset

Real-world applications

Digitizing Carbon Credits on Blockchain is no longer just a theoretical idea - several projects have already put it into practice:

04 · BLOCKCHAIN, CRYPTOGRAPHY & CONSENSUS

What is Blockchain? Cryptography & Consensus Mechanisms

A Blockchain is an append-only database made up of blocks tightly linked together using cryptographic hash functions.

The chain structure is linked via the previous block's hash (Parent Hash):

BLOCK 1
ID1
Parent Hash0x000...
Timestamp1718000000
Transactions[...]
BLOCK 2
ID2
Parent HashHash(B1)
Timestamp1718000012
Transactions[...]

↓ Block 2 links to Block 1 via Parent Hash = Hash(Block 1).

Traditional databases vs Blockchain

CriteriaTraditional databaseBlockchain
ModelCentralizedDistributed
ManagementA single organization / AdminA network of many Nodes
Data modificationCan overwrite/delete (CRUD)Append-only
ConsensusNot requiredMandatory (PoW, PoS...)
Transparency & AuditDepends on the system logTransparent, publicly encoded

Data storage: Centralized (SQL Server, MySQL) vs Distributed (Blockchain)

With SQL Server or MySQL, all the data lives in one place (or one server cluster fully controlled by a single organization): the client sends a query, the server processes it, and the result comes from exactly one copy of the data. With Blockchain, every Node in the network keeps its own full copy of the data, and that copy is only updated once a majority of Nodes reach consensus.

CENTRALIZED (SQL Server, MySQL...) Client ──▶ 1 Server ──▶ 1 single copy of the data (Admin/DBA has full UPDATE, DELETE rights) DISTRIBUTED (Blockchain) Client ──▶ Node 1 ─┐ Node 2 ─┼─ Consensus (PoW/PoS) ──▶ Every Node holds an identical copy Node 3 ─┘ (No single party can unilaterally change it)

Direct consequences of these two storage models:

  • Single point of failure: if SQL Server/MySQL goes down, the whole system stops; Blockchain keeps running because thousands of other Nodes still hold a copy of the data.
  • Trust model: with MySQL, users have to trust the Admin/DBA of the organization that owns the server not to quietly alter the data; with Blockchain, no single party needs to be trusted - data is only recorded once a majority of Nodes in the network reach consensus.
  • Ability to modify/delete data: UPDATE/DELETE work normally on MySQL; Blockchain only supports appending (INSERT, append-only) - "correcting" a past transaction means writing a new transaction that reverses it, while the original data stays in the history.
  • Performance & storage cost: MySQL writes once on one server, so it's fast and cheap; Blockchain has to replicate data across every Node and run a consensus mechanism before writing, making it slower and far more expensive to store.
A system design principle: Don't adopt Blockchain just because it's trendy. It must start from Problem Statement ➜ Requirement Analysis ➜ Blockchain Suitability - if the problem doesn't genuinely need decentralization or tamper-resistance, a centralized database like MySQL is still the cheaper, faster choice.

Asymmetric-key cryptography & Digital Signatures

User authentication relies on a key pair: a Private Key (kept secret, used to sign transactions) and a Public Key (public, used by the network to verify).

Message + Private Key ➜ Digital Signature Signature + Message + Public Key ➜ Verification (True / False)

PoW vs PoS & environmental impact

  • Proof of Work (PoW): Uses computational power (Mining) to solve a cryptographic puzzle. Very secure, but consumes a huge amount of electricity.
  • Proof of Stake (PoS): Uses staked assets (Stake) to select a Validator to create the next block. Cuts power consumption by more than 99.9% compared to PoW.

A model for estimating On-chain Carbon Footprint:

Carbon Emission (tCO₂e) = Energy Consumption (kWh) × Emission Factor (kgCO₂e/kWh)

06 · CRYPTOGRAPHY DEMO

Cryptography demo: Creating a Block & a digital signature in Python

Example 1: Simulating a linked Hash chain (basic Blockchain)

Create the file simple_chain.py:

import hashlib
import json

class Block:
    def __init__(self, block_id, history, parent_hash="0"):
        self.id = block_id
        self.history = history
        self.parent_hash = parent_hash

    def compute_hash(self):
        block_string = json.dumps(self.__dict__, sort_keys=True)
        return hashlib.sha256(block_string.encode('utf-8')).hexdigest()

# Tạo Genesis Block
block_A = Block(1, "Ty likes cat")
hash_A = block_A.compute_hash()

# Tạo Block kế tiếp
block_B = Block(2, "Teo likes dog", parent_hash=hash_A)
hash_B = block_B.compute_hash()

print(f"Block A Hash: {hash_A}")
print(f"Block B Parent Hash: {block_B.parent_hash}")

Example 2: Generating keys & signing a digital signature with the cryptography library

Create the file digital_signature_demo.py:

from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes, serialization

# 1. Tạo cặp khóa RSA
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

# 2. Tạo thông điệp và ký chữ ký số
message = b"Ty likes cat"
signature = private_key.sign(
    message,
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256()
)

# 3. Xác thực chữ ký số thành công
try:
    public_key.verify(
        signature,
        message,
        padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
        hashes.SHA256()
    )
    print("Xác thực chữ ký hợp lệ!")
except Exception as e:
    print("Chữ ký KHÔNG hợp lệ!", e)

Vyper: Basic syntax & data types

Vyper is a programming language designed for the EVM that prioritizes safety, with syntax similar to Python. Create the file DataType.vy:

# @version ^0.4.3

# Kiểu dữ liệu cơ bản
is_active: bool
var_int: int128
var_uint: uint256
owner_wallet: address
data_hash: bytes32
author_name: String[100]

# Struct & Mapping
struct Permission:
    write: bool
    execute: bool

my_permission: Permission
donations: HashMap[address, uint256]

@deploy
def __init__():
    self.is_active = True
    self.var_uint = 100
    self.owner_wallet = msg.sender
    self.author_name = "IS355 Student"
    self.my_permission = Permission(write=True, execute=False)

09 · VYPER: SCOPE & MUTABILITY

Vyper: Scope & Mutability Annotations

Create the file Annotations.vy:

# @version ^0.4.3

stored_data: uint256

# @pure: Không đọc, không ghi dữ liệu trạng thái
@external
@pure
def add(x: uint256, y: uint256) -> uint256:
    return x + y

# @view: Chỉ đọc dữ liệu trạng thái, không thay đổi trạng thái
@external
@view
def read_data() -> uint256:
    return self.stored_data

# @nonpayable: Thay đổi trạng thái nhưng KHÔNG nhận ETH
@external
@nonpayable
def set_data(new_value: uint256):
    self.stored_data = new_value

# @payable: Thay đổi trạng thái và CÓ THỂ nhận ETH
@external
@payable
def deposit():
    assert msg.value > 0, "So tien gui phai lon hon 0"

11 · PART D - DATA & RESEARCH

Modeling a Carbon Footprint forecasting problem from On-chain data

On-chain Data ↓ Data Preprocessing ↓ Feature Engineering ↓ ML Model ↓ Carbon Emission Prediction

Suggested dataset (Features & Target)

  • X (Features): Transaction Count, Active Addresses, Gas Used, Network Hashrate / Active Validators.
  • Y (Target): Estimated Carbon Emission (tCO₂e).

Recommended research process

  1. Survey historical data from On-chain Explorer sources (Etherscan, Green Software Foundation API)
  2. Build a Baseline Model (Linear Regression)
  3. Experiment with Traditional ML Models (Random Forest, XGBoost)
  4. Evaluate using MAE, RMSE, R² metrics
