01 · PART A - LECTURE THEORY

From real assets to digital assets (Tokenization)

In traditional finance, assets exist as stocks, bonds, certificates, or Carbon Credits. Blockchain makes it possible to standardize and digitize these ownership/usage rights.

Real asset / Credit ↓ Verification ↓ Tokenization ↓ Blockchain Token ↓ Trade / Transfer
Example: 1 verified Carbon Credit (1 tCO₂e) ➜ encoded as 1 Carbon Token on the Blockchain.

02 · COIN VS TOKEN

Distinguishing Coin from Token

TraitCoin (Native network)Token (Smart Contract asset)
NatureThe base currency of its own BlockchainCreated via a Smart Contract running on an existing platform
ExampleEthereum (ETH), Bitcoin (BTC)USDT, USDC, Green Carbon Token (GCT)
RulesFollows the Blockchain's Consensus LayerFollows the programmed logic in the Smart Contract (e.g., the ERC-20 standard)

03 · CARBON CREDIT VS CARBON TOKEN

Carbon Credit vs Carbon Token & "Garbage In, Garbage Out"

Carbon Credit ≠ Carbon Token: A Carbon Credit is a legal/environmental certificate tied to an off-chain verification standard. A Carbon Token is merely the vehicle that represents that asset on the Blockchain.
"Garbage In, Garbage Out" risk: Blockchain guarantees data cannot be altered once written, but it does not itself verify the correctness of the input data. If a company overstates its emission reductions, the Blockchain will store that fabricated figure with perfect accuracy.

Solution: Must combine independent auditing (Auditor), Certification, and an Oracle layer to verify data before minting Tokens.

04 · THE ERC-20 STANDARD

The ERC-20 standard and its core functions

The ERC-20 standard defines the required interface for a Fungible Token:

  • balanceOf(account): Looks up the balance of the account address
  • transfer(to, amount): Transfers amount tokens from the function caller (msg.sender) to to
  • approve(spender, amount) & transferFrom(sender, recipient, amount): The allowance mechanism, letting wallet A authorize contract B to spend up to a set amount of Token on its behalf - The foundation for DeFi, DEX, Staking, and Carbon payment gateway applications

05 · MINT, BURN & CARBON RETIREMENT

Mint, Burn, and Carbon Retirement mechanics

  • Mint (Issuance): Creates new Tokens when a project adds a newly verified Carbon Credit (Total Supply increases)
  • Burn / Retire: When a company uses a Carbon Token to Offset emissions, that Token must be burned out of circulation (Total Supply decreases)
Why it matters: This entirely eliminates the risk of Double Counting/Double Use - The same credit being used to offset for multiple different parties.

06 · PART B - SMART CONTRACT PROGRAMMING PRACTICE (VYPER)

The GreenCarbonToken.vy Smart Contract structure

# @version ^0.4.3

"""
@title Green Carbon Token (GCT) - ERC-20 Implementation
@notice Smart Contract quản lý Token Carbon phục vụ tài chính bền vững
"""

# Các sự kiện (Events)
event Transfer:
    sender: indexed(address)
    receiver: indexed(address)
    value: uint256

event Approval:
    owner: indexed(address)
    spender: indexed(address)
    value: uint256

event CarbonRetired:
    owner: indexed(address)
    amount: uint256
    carbon_offset_reason: String[100]

# Biến trạng thái (State Variables)
name: public(String[32])
symbol: public(String[8])
decimals: public(uint8)
total_supply: public(uint256)

balances: public(HashMap[address, uint256])
allowances: public(HashMap[address, HashMap[address, uint256]])

admin: public(address)

@deploy
def __init__():
    self.name = "Green Carbon Token"
    self.symbol = "GCT"
    self.decimals = 18
    self.total_supply = 0
    self.admin = msg.sender

@view
@external
def balanceOf(account: address) -> uint256:
    return self.balances[account]

@external
def transfer(to: address, amount: uint256) -> bool:
    assert to != empty(address), "Invalid receiver"
    assert self.balances[msg.sender] >= amount, "Insufficient balance"

    self.balances[msg.sender] -= amount
    self.balances[to] += amount

    log Transfer(msg.sender, to, amount)
    return True

@external
def approve(spender: address, amount: uint256) -> bool:
    assert spender != empty(address), "Invalid spender"

    self.allowances[msg.sender][spender] = amount
    log Approval(msg.sender, spender, amount)
    return True

@external
def transferFrom(sender: address, recipient: address, amount: uint256) -> bool:
    assert recipient != empty(address), "Invalid recipient"
    assert self.balances[sender] >= amount, "Insufficient balance"
    assert self.allowances[sender][msg.sender] >= amount, "Insufficient allowance"

    self.allowances[sender][msg.sender] -= amount
    self.balances[sender] -= amount
    self.balances[recipient] += amount

    log Transfer(sender, recipient, amount)
    return True

@external
def mint(to: address, amount: uint256):
    # Access Control: Chỉ Admin/Issuer mới được phát hành
    assert msg.sender == self.admin, "Access Denied: Only Admin can mint"
    assert to != empty(address), "Invalid address"

    self.total_supply += amount
    self.balances[to] += amount

    log Transfer(empty(address), to, amount)

@external
def burn(amount: uint256):
    assert self.balances[msg.sender] >= amount, "Insufficient balance to burn"

    self.balances[msg.sender] -= amount
    self.total_supply -= amount

    log Transfer(msg.sender, empty(address), amount)

@external
def retireCarbon(amount: uint256, reason: String[100]):
    """
    @notice Tiêu hủy Token để thực hiện Offset phát thải và cấp chứng nhận
    """
    assert self.balances[msg.sender] >= amount, "Insufficient balance to retire"

    self.balances[msg.sender] -= amount
    self.total_supply -= amount

    log Transfer(msg.sender, empty(address), amount)
    log CarbonRetired(msg.sender, amount, reason)
Why does Access Control matter? If the line assert msg.sender == self.admin is removed, anyone could call mint() for an arbitrary amount, letting Total Supply grow without bound and breaking the Tokenomics. A Smart Contract is not just code - Function execution rights are also part of the financial design.

07 · TESTING WITH APE FRAMEWORK

Test & interaction script (Ape Framework Script)

Create the file scripts/interact_gct.py to test the flow:

from ape import accounts, project

def main():
    # Load tài khoản đại diện
    admin = accounts.test_accounts[0]
    alice = accounts.test_accounts[1]
    bob = accounts.test_accounts[2]

    # 1. Triển khai Contract
    gct = admin.deploy(project.GreenCarbonToken)
    print(f"Contract Deployed at: {gct.address}")

    # 2. Mint Token cho Alice (Admin thực hiện)
    gct.mint(alice.address, 1000 * 10**18, sender=admin)
    print(f"Alice Balance after Mint: {gct.balanceOf(alice.address) / 10**18} GCT")

    # 3. Alice chuyển Token cho Bob
    gct.transfer(bob.address, 200 * 10**18, sender=alice)
    print(f"Bob Balance: {gct.balanceOf(bob.address) / 10**18} GCT")

    # 4. Alice retire 300 GCT để offset phát thải nhà máy
    gct.retireCarbon(300 * 10**18, "Offset emissions for Q3 2026", sender=alice)
    print(f"Alice Balance after Retirement: {gct.balanceOf(alice.address) / 10**18} GCT")
    print(f"Total Supply after Retirement: {gct.total_supply() / 10**18} GCT")

    # 5. Thử nghiệm Access Control: Bob gọi mint (kỳ vọng fail/revert)
    try:
        gct.mint(bob.address, 500 * 10**18, sender=bob)
    except Exception as e:
        print("Access Control Verified: Bob cannot mint Token!")

08 · PART C - DATA & RESEARCH

Research 1: Forecasting Carbon Credit prices

Problem statement: Forecast future Carbon Credit price movements based on historical trading data, energy prices, and emission policy.

Process (Data Pipeline)

Data Collection ↓ Preprocessing ↓ Feature Engineering ↓ Model Selection ↓ Evaluation
  • Data Collection: Gather Time Series data on Carbon Credit prices, coal/gas prices, and industrial production indices
  • Preprocessing: Handle missing values, normalize data (MinMax Scaling)
  • Feature Engineering: Build technical indicators (Moving Average, RSI, Volatility Index)
  • Model Selection: Baseline (Moving Average/ARIMA) ➜ Machine Learning (XGBoost, Random Forest Regressor) ➜ Deep Learning (LSTM)
  • Evaluation: Assess using MAE, RMSE, and MAPE

09 · ADAPTIVE TOKEN ISSUANCE

Research 2: Adaptive Carbon Token Issuance

Issue Tokens based on an off-chain data risk score, instead of a fixed 1 Carbon Credit = 1 Token conversion.

Carbon survey data ↓ Machine Learning Risk Model ↓ Risk Score (0-100%) ↓ Chainlink Oracle Node ↓ Chainlink Oracle Callback ↓ Smart Contract Mint Limit

Architecture idea: Don't issue 100% of Tokens if the Carbon data hasn't been fully verified. Mechanism:

  1. An off-chain ML model analyzes satellite imagery/IoT sensor data from a forestry or green energy project
  2. It computes a data confidence score (e.g., 85% confidence)
  3. The risk score is passed into the Smart Contract via an Oracle
  4. The Smart Contract applies a flexible mint formula
Mint Limit = Verified Credits × Confidence Score
